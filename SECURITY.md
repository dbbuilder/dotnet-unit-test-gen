## Reporting a Vulnerability

We take security seriously. If you discover a security vulnerability, please follow these steps:

### 1. **DO NOT** create a public GitHub issue

Public disclosure of security vulnerabilities can put users at risk. Please report privately.

### 2. Report via GitHub Security Advisories

- Go to the [Security tab](https://github.com/dbbuilder/dotnet-unit-test-gen/security)
- Click "Report a vulnerability"
- Provide details about the vulnerability

### 3. Or email directly

Send details to: [INSERT SECURITY EMAIL]

Include:
- Description of the vulnerability
- Steps to reproduce
- Potential impact
- Suggested fix (if any)

### 4. Response Timeline

- **24-48 hours**: Initial acknowledgment
- **7 days**: Assessment and severity classification
- **30 days**: Fix development and testing
- **Coordinated disclosure**: We'll work with you on public disclosure timing

## Security Considerations

### API Key Safety

- **Never commit API keys** to the repository
- Use `.env` files (already in `.gitignore`)
- Rotate keys if accidentally exposed
- Use environment variables in production

### AI Provider Security

- API keys are sent to third-party services (OpenAI, Anthropic, Google)
- Generated code should be reviewed before use
- Test in isolated environments first
- Be aware of data sent to AI providers

### Generated Code Review

**IMPORTANT**: AI-generated test code should be reviewed before deployment:

- Review mocking logic for security implications
- Check for hardcoded credentials in generated tests
- Verify test isolation (no shared state)
- Ensure tests don't expose sensitive data

### Dependencies

- Run `pip audit` regularly to check for vulnerable dependencies
- Keep Python and dependencies updated
- Review requirements.txt changes in PRs

## Best Practices

### For Users

1. **Keep software updated** to latest stable version
2. **Use virtual environments** to isolate dependencies
3. **Review generated tests** before committing to production
4. **Protect API keys** using secrets management
5. **Run in sandboxed environments** when testing unknown code

### For Contributors

1. **Never commit sensitive data** (keys, credentials, personal info)
2. **Sanitize logs** before sharing (remove API keys, paths)
3. **Review dependencies** before adding new ones
4. **Use type hints** to catch potential issues early
5. **Add security tests** for new features

## Known Limitations

### AI-Generated Code

- Tests are generated by AI and may have logical errors
- Generated code should not be trusted blindly
- Always review before using in production

### API Provider Risks

- Your code is sent to third-party AI services
- Check your organization's data policy before using
- Consider self-hosted models for sensitive codebases

### Rate Limiting

- No built-in rate limiting (depends on AI provider)
- Large codebases may exceed API quotas
- Use `--dry-run` to estimate costs first

## Security Updates

Security fixes will be released as soon as possible:
- **Critical**: Within 24-48 hours
- **High**: Within 7 days
- **Medium**: Next minor release
- **Low**: Next major release

## Responsible Disclosure

We believe in coordinated disclosure:
1. Reporter privately discloses vulnerability
2. We develop and test fix
3. We release security patch
4. Public disclosure after fix is available
5. Credit given to reporter (if desired)

## Questions?

For general security questions (not vulnerabilities), create an issue with the `security` label.
